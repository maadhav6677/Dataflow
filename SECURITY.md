# Security policy

## Supported versions

This repository is a demonstration product without long-term-support releases. Security fixes are applied only to the latest commit on the default branch.

| Version | Supported |
|---|---|
| Latest default-branch revision | Yes |
| Older commits, forks, and modified deployments | No |

## Data classification and privacy boundary

Every business record is generated by `src/generate_data.py`. The dataset contains no real customer, supplier, employee, contact, credential, confidential, scraped, or production data.

The generated manifest asserts:

- `synthetic: true`
- `contains_personal_data: false`
- a deterministic seed and observation period
- expected row counts for every source file

Synthetic identifiers are non-identifying surrogate keys. Names used for suppliers and products are fictional demonstration labels.

Do not replace the synthetic inputs with real data unless the deployment receives an independent privacy, access-control, retention, and security review.

## Threat model

### In scope

- accidental publication of private data or secrets;
- malicious or malformed CSV input reaching the warehouse;
- broken relational integrity or unsafe value ranges;
- partially written analytical artifacts after an interrupted build;
- third-party browser scripts or hidden outbound dashboard requests;
- CI permissions and reproducibility of published outputs;
- unsafe HTML insertion from generated display fields.

### Outside the current product boundary

- authentication and authorization, because the dashboard has no user accounts or backend;
- internet-facing server hardening, because the documented server is for local static preview only;
- encryption at rest, key management, audit logging, rate limiting, and tenant isolation;
- production ERP, WMS, TMS, database, or API integrations;
- security properties of downstream systems that import the CSV exports;
- modified forks that add third-party dependencies, external data, or hosting.

The absence of those controls is acceptable only inside the documented local synthetic-data scope. They are required design work before production deployment.

## Implemented controls

| Area | Control |
|---|---|
| Dependencies | The Python pipeline uses the standard library only; the dashboard has no third-party runtime scripts |
| Secrets | No credential, token, key, `.env` file, or external service is required |
| Input schemas | Exact CSV header order is validated before load |
| Input types | Numeric conversions fail closed with file and line context |
| Value integrity | SQLite `CHECK` constraints enforce ranges and controlled values |
| Relationships | Primary keys, foreign keys, and `PRAGMA foreign_key_check` validate references |
| Business rules | Customer/warehouse cities, supplier/product categories, activation dates, and success labels are validated |
| Privacy manifest | Build fails if the manifest does not assert synthetic data without personal information |
| Atomic publishing | Database, manifest, dashboard payload, and report files are written through temporary paths |
| Browser behavior | No trackers, forms, cookies, CDN assets, fetch calls, or outbound dashboard requests |
| HTML safety | Dashboard display strings are escaped before HTML insertion |
| CI | Workflow permissions are limited to read-only repository contents |
| Reproducibility | CI rebuilds and rejects drift in committed analytical outputs |

## Safe local operation

- Run the dashboard only from a trusted checkout.
- Use `python3 -m http.server` only for local preview; do not expose it as a production web server.
- Treat manually supplied CSV files as untrusted even if they match the schema.
- Do not commit the generated SQLite database or raw CSV files.
- Review `git diff` before committing generated reports or dashboard data.
- Never paste secrets or private datasets into bug reports, screenshots, reports, or test fixtures.
- Do not weaken validation to make an external dataset load successfully; add an explicit governed ingestion step instead.

## Dependency and supply-chain policy

The project intentionally has no third-party Python or browser runtime dependencies. Development and CI still rely on Python, Git, GNU Make, GitHub Actions, and the operating system.

If a dependency is proposed:

1. Document why the current standard-library approach is insufficient.
2. Review the package owner, release history, license, transitive dependencies, and known vulnerabilities.
3. Pin an appropriate version or immutable action revision.
4. Update the architecture, setup, lockfile strategy, and this policy.
5. Add tests proving the dependency does not introduce outbound requests or private-data handling unexpectedly.

## Production deployment requirements

This repository is not a production deployment template. A production implementation must add, at minimum:

- authenticated users and least-privilege authorization;
- governed secrets and configuration management;
- encrypted transport and appropriate encryption at rest;
- source-system access controls and privacy classification;
- input provenance, retention, deletion, and audit policies;
- monitored scheduling, logs, metrics, alerts, and incident response;
- dependency scanning and patched base runtimes;
- output access controls and row- or tenant-level isolation where required;
- a threat model covering the chosen hosting environment.

## Reporting a vulnerability

Do not open a public issue containing exploit details, secrets, private data, or a proof of concept.

Use the repository host's private vulnerability-reporting feature if it is enabled. Otherwise, contact the repository owner through a private channel published on their profile and include only enough non-sensitive information to establish contact first.

After a private channel is established, provide:

- the affected revision and file;
- impact and realistic attack scenario;
- reproduction steps using synthetic data only;
- whether the issue is already public;
- a suggested fix, if available.

You should receive acknowledgement when the owner reviews the report. Because this demonstration has no dedicated security team or service-level agreement, do not assume a fixed response timeline.
